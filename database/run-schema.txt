## Supabase schema runbook

This directory contains ordered migrations, conditional legacy/repair scripts,
one read-only verification script, and one operator-only role-promotion script.
Do not run every `.sql` file as one batch.

For a new Supabase project, apply migrations 1–17 in order using a trusted
Supabase SQL Editor session with a privileged database role. For an existing
project, inspect its schema and migration history, then apply only the missing
ordered migrations in this sequence. Do not put database credentials in browser
code or run schema changes from a storefront.

### Ordered migrations

1. database/schema.sql — extensions and core profiles, shops, products, orders, order items, conversations, deletion requests, and operational events.
2. database/seller.sql — seller-role helper and operator-only promotion functions; requires schema.sql.
3. database/admin.sql — admin-role helper and operator-only promotion functions; requires schema.sql. It does not promote an account.
4. database/supabase-rls.sql — base table, Storage, seller ownership, and product-media quota policies; requires schema.sql.
5. database/security-hardening.sql — profile authorization helpers, protected profile fields, and server-side rate-limit storage; requires steps 1–4 and must precede dashboard RPCs.
6. database/cloudflare-dashboard.sql — dashboard RPCs, participant-only messaging, listing moderation, and guarded admin queues; requires steps 1–5.
7. database/cloudflare-supabase-direct.sql — direct Supabase account-deletion and related browser-safe RPCs; requires steps 1–6 and data_deletion_requests from schema.sql or the legacy script below.
8. database/production-hardening.sql — secure, idempotent checkout RPC and order-write protections; requires schema, seller, RLS, security-hardening, and dashboard migrations.
9. database/shop-owner-payments.sql — standalone shop-owner portal, payout references, and regional payment records; requires steps 1–6 and 8.
10. database/shop-verification-compliance.sql — private verification submissions and guarded approval workflow; requires shop-owner-payments.sql.
11. database/seller-contact-safety.sql — opt-in public seller contact and offline checkout safeguards; requires schema, RLS, production-hardening, shop-owner-payments, and shop-verification-compliance.
12. database/product-delivery-options.sql — seller-provided delivery options; requires schema.sql.
13. database/client-error-logging.sql — sanitized operational-event types and server-only event access; requires operational_events from schema.sql.
14. database/marketplace-manual-payments.sql — KYC-gated manual payment preferences, regional destination settings, order instruction snapshots, and recipient-specific confirmations; requires migrations 1–13.
15. database/marketplace-media-settings.sql — seller-friendly, admin-controlled listing counts and media sizes with database enforcement and fixed Storage ceilings; requires migrations 1–14.
16. database/account-deletion-status.sql — lets an authenticated requester view only their latest deletion-request status; requires migration 7 and does not perform account or data deletion.
17. database/student-listing-submission-fixes.sql — fixes listing submission against schemas without products.image_url and accepts current Supabase Storage contentLength metadata; requires migrations 6 and 15.

Before applying step 15 to any Supabase project, verify the project's actual
plan and global Storage file-size limit in the dashboard. Both must support at
least 40 MiB (41,943,040 bytes). The documented Free-plan maximum is not
evidence of a target project's configured limit. Keep the 10-item listing
quotas; the 40 MiB value is a per-file ceiling.

The order keeps the security helpers ahead of dashboard RPCs, checkout
hardening ahead of shop-owner payment functions, verification before seller
contact/payment preferences, and the media-settings migration after the
manual-payment dependencies it requires.
Steps with only a schema.sql dependency are kept in this sequence so fresh
projects have one consistent run order.

### Conditional legacy and repair scripts

Apply these separately only when their condition is confirmed:

- database/account-deletion.sql — legacy databases that predate the deletion-request objects in schema.sql; apply after schema.sql and before step 7. New databases already receive these objects from schema.sql.
- database/fix-product-media-delete-ambiguity.sql — existing databases affected by PostgreSQL error 42702 during product-media cleanup; apply after step 4, supabase-rls.sql.
- database/storage-public-bucket-list-policy-fix.sql — existing projects where broad legacy SELECT policies still allow product-media bucket listing; apply after step 4. It removes object-listing policies while keeping known public object URLs usable.

Run `npm run test:storage-policy-safety` before applying or changing storage
policies. Do not apply either repair script to a new project unless its stated
condition is present.

### Verification and operator-only SQL

- database/safety-verification.sql — run after all applicable ordered and conditional migrations. It is read-only; it checks schema, grants, and RLS metadata but does not prove authenticated user behavior.
- database/promote-admin.sql — operator-only example, not a migration. Replace the placeholder with the email of an already-registered user and run only in a trusted Supabase SQL Editor transaction after the ordered migrations. Never run it from a browser or expose role-promotion functions to anon/authenticated users.

The `admin.sql` and `seller.sql` files define restricted promotion functions;
they do not promote any account automatically. For a seller repair, use the
same transaction-local service_role pattern with assign_seller_role.

For authenticated behavior checks, use docs/staging-acceptance.md with a
dedicated non-production project and disposable accounts. Read-only SQL checks
cannot prove live upload, checkout, or account-deletion behavior.
